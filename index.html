Inkwell

Real-Time Stylized Rendering with Temporally Coherent Strokes

Summary

We will build a real-time non-photorealistic renderer that runs in the browser and can draw any 3D model in several hand-made styles, including toon shading, ink outlines, hatching, halftone dots and watercolor. Beyond implementing the styles, we will focus on temporal coherence, so that strokes and textures stay attached to the surface when the camera or the object moves instead of sliding across it, and we will measure how well each method does this.

Problem Description

Everything we rendered in the homeworks aimed to be physically correct. Artists and illustrators often want the opposite, an image that looks drawn or painted, because a few clean lines and flat tones can communicate shape more clearly than a photorealistic render. This is used in games, animated films, technical illustration and architectural drawings. Non-photorealistic rendering (NPR) generates these styles from 3D scenes automatically.

Single stylized frames are fairly easy to produce with image filters. The hard part is animation. Most simple stylization methods work in screen space, so a hatching pattern or a grid of halftone dots stays fixed on the screen while the object moves underneath it. This is called the shower-door effect, and it immediately breaks the illusion that the image was drawn. The obvious fix, attaching the texture to the surface, has its own problem. As the object moves closer or further away, the strokes grow and shrink, so their density and line width no longer match the look of a drawing. Lines have similar issues, since edges detected per frame flicker as they appear and disappear. Balancing these two goals, strokes that follow the surface but still look like they were drawn at a constant scale on paper, is the main challenge of this project.

Our approach is to build all styles on top of a shared real-time pipeline in WebGL. A first pass renders a G-buffer with depth, normals, lighting and texture coordinates, and each style is a combination of shading in that pass and image-space post-processing. For temporal coherence, we will implement object-space tonal art maps for hatching, which blend between stroke textures of different densities with mipmapping, and compare them against our screen-space versions on the same camera paths.

Goals and Deliverables

What we plan to deliver

Our baseline is an interactive web demo where the user can load a model, orbit around it, move the light, and switch between styles live. Each of us is responsible for one family of styles.

  • Toon shading. Lighting quantized into a small number of bands, color ramps, rim lighting and stylized specular highlights.
  • Lines. Silhouette and crease lines, using both an inverted-hull outline and edge detection on the depth and normal buffers, with adjustable width.
  • Texture-based tone. Screen-space hatching, cross-hatching, halftone dots and stippling, where the density of the pattern follows the lighting.
  • Painterly and poster styles. Posterization to a fixed palette, a Kuwahara filter for a painted look, and a basic watercolor effect with paper texture and darkened edges.

Any style can be combined with the line pass, so for example toon shading can be drawn with or without ink outlines. We will deliver the demo, a set of still renders of each style on several models, and a short video of the styles on moving scenes.

What we hope to deliver

  • Temporal coherence. Object-space hatching with tonal art maps, and a comparison against the screen-space version on the same camera paths. This is our first priority if we are ahead of schedule.
  • Watercolor. A more complete watercolor model with pigment pooling at edges, color bleeding between regions and wobbly, hand-drawn edges.
  • Suggestive contours. Lines at places that are almost silhouettes, which show the inner shape of a model much better than silhouettes alone, computed from the mesh curvature.
  • Style blending and a short film. Smooth transitions between styles, assigning different styles to different objects, and a short animated scene that shows them off.

How we will measure success

  • Performance. Frame rate of each style at 1920×1080 on our laptops, for models from about 10,000 to 1,000,000 triangles. Our target is 60 frames per second for every baseline style on typical models.
  • Temporal coherence. For a fixed camera path, the average pixel difference between consecutive frames in the stroke regions, comparing screen-space and object-space versions of the same style. Lower flicker for the same amount of motion means the strokes follow the surface better.
  • Visual quality. Side-by-side comparisons with real hand-drawn and painted references of similar objects.

Questions we want to answer

  • Which stylization effects can run at interactive frame rates in a browser, and which ones are too expensive?
  • How much does object-space texturing reduce flicker compared to screen-space texturing, and what does it cost in look and performance?
  • Which line detection method gives the cleanest lines across different kinds of models?

Resources

Computing platform, hardware and software

  • JavaScript with three.js and WebGL 2 and GLSL shaders, running in the browser.
  • Our own laptops, including Apple Silicon Macs, so that the demo runs anywhere without special hardware.
  • Test models from the Stanford 3D Scanning Repository and free glTF models, plus the meshes from the homeworks.

Starting point

We are starting from an empty three.js project and are not using any existing NPR code. three.js only provides model loading, the camera and the WebGL setup, and all of the stylization shaders and post-processing passes are our own.
